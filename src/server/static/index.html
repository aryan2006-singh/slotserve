01 — Why

Static batches wait for the slowest request.

With static batching, every request in a batch waits for the longest one, and finished rows burn compute on padding. Continuous batching re-forms the batch every decode step instead. Same eight requests, four slots:

Static batching

done at step 14
step 014

Request C needs 2 steps but its slot is stuck until step 8. Hatched blocks are wasted compute.

Continuous batching

done at step 11
step 014

When C finishes at step 2, E takes its slot straight away. No padding, and everything finishes sooner.

02 — How it works

One loop. Three moves. Every step.

A single engine thread runs this loop. The KV cache is one preallocated tensor with a fixed row per slot, so requests can join and leave without reshuffling anyone else.

01

Admit & prefill

If a slot is free, take the next queued request and run its prompt through the model. At most one prefill per step keeps token timing smooth for everyone already decoding.

02

Decode everyone, one token

Every running request advances by exactly one token in a single batched forward pass. A 4D attention mask hides each row's unwritten positions, so different lengths share one batch safely.

03

Release finished slots

A request that hits its stop token or token limit frees its slot immediately. On the very next step, a queued request moves in, and the GPU or CPU never idles on padding.

03 — Features

Small server. Serious engine.

Built from first principles to make batching visible and verifiable, not to hide it behind a framework.

01

Token-level continuous batching

The batch is rebuilt every decode step, so throughput no longer depends on the unluckiest request.

02

Slot-addressed KV cache

One preallocated tensor per layer. Each request owns a row, so joining and leaving costs nothing.

03

OpenAI-compatible API

/v1/completions and /v1/chat/completions with streaming. Point the official client straight at it.

04

Verified output

27 tests compare greedy output against HF generate(), covering mid-flight arrivals, slot reuse and stop tokens.

05

Live metrics

/stats shows every slot in real time, and /metrics speaks Prometheus. The chat page draws both.

06

Free to run

Works on a laptop CPU with SmolLM2-135M, ships a Dockerfile, and deploys to Hugging Face Spaces on the free tier.

from openai import OpenAI

client = OpenAI(base_url="http://localhost:8000/v1", api_key="none")

stream = client.chat.completions.create(
    model="slotserve",
    messages=[{"role": "user", "content": "Explain continuous batching"}],
    stream=True,
)
for chunk in stream:
    print(chunk.choices[0].delta.content or "", end="")

05 — Honest trade-offs

What it doesn't do (yet).

Every design choice has a cost. These are the ones that matter most, and where the project goes next.

One prefill per step

Smooth token timing, but a burst of new arrivals is admitted one at a time.

next: chunked prefill

No preemption

An admitted request keeps its slot until it finishes, so slots can't be oversubscribed.

next: swap or recompute

Padded reads

Attention reads each window padded to the longest sequence. This is the biggest gap to vLLM at large batch sizes.

next: paged attention
